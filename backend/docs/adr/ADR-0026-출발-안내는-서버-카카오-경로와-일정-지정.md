# ADR-0026 — 출발 안내는 서버가 카카오 경로로 구하고 일정은 앱이 지정

- 상태: **채택(일부 대체 → ADR-0028)** (2026-11-13)
- ADR-0028이 도착 목표를 "하원 시각 − 10분"에서 "하원 시각 + 아이 도보 시간 − 대기 여유"로 바꿨다.
- ADR-0022의 "차량 소요 시간은 앱이 보낸 `driveMin`(NaviHelper `eta`)"과 "서버는 요청 중에 외부 교통 API를 부르지 않는다"를 대체한다. 이력 보정(`TRAFFIC_PROFILE`)은 그대로다.
- ADR-0023의 경로 시작 요청에서 "오늘 진행 중 계획·오늘 남은 픽업을 사용자 단위로 고르는 것"을 대체한다.
- 사용자가 2026-11-13에 고른 결정이다(T87).

## 결정

- 출발 안내(`DetailDepartureGuide`)의 차량 시간은 앱의 `driveMin`을 받지 않고, 서버가 카카오모빌리티 자동차 길찾기를 요청마다 1회 불러 구한다(현재 위치 → 픽업 장소 → 집). 호출이 실패하면 직선 거리 추정(`ESTIMATE`)으로 돌아간다. 결과는 저장하지 않는다.
- 추천 출발은 "도착 목표 − 차량 시간 − 혼잡 보정"이다. 도착 목표는 하원 시각보다 `DepartureGuide:ArriveBeforeEndMin`(기본 10분) 먼저 픽업 장소에 닿는 시각이다(기획 "하원 10분 전 도착"). 예전의 "배정 시각 − 차량 시간 − 여유 1분"을 대신한다. 배정 시각(`slotDt`)과 아이 도착은 정원 관리용으로 그대로 둔다.
- 혼잡 보정(`ROAD_CONGESTION`)은 차량 시간이 카카오 값(`driveRoute.source = ROUTE`)일 때 적용하고, 비교하는 계획 시각은 도착 목표다.
- 출발 안내·대기 장소·경로 시작은 요청의 `scheduleSeq`(시간표 ID)로 일정을 지정한다. 서버가 사용자 단위로 일정을 고르던 로직은 없앤다. 출발 안내·대기 장소는 `dayOfWeek`도 받아 서버 오늘 요일과 다르면 101이고 하원 뒤 시간 창이 없다. 경로 시작은 기존 시간 창(하원 + `PickupWindowHours`)을 유지한다.
- 화면 분기(출발 전 화면에서 지금 출발이면 픽업 장소 안내, 10분 이상 남았으면 대기 장소)는 앱이 `slackMin`으로 한다.

## 근거

- 화면 07_RM-V03 오늘의 픽업(출발 전)에 현재 위치 → 픽업 장소 → 집 경로와 총 시간, 집 도착 예상이 필요하다. 앱이 보내는 값 하나(`driveMin`)로는 구간별 시간과 집 도착을 만들 수 없다.
- 기획은 "하원 10분 전 도착"이다. 배정 시각 기준은 정원 관리에는 맞지만 부모가 기대하는 출발 시각과 다르다.
- 아이와 일정이 여럿이면 서버가 자동으로 고른 일정이 부모가 보고 있는 일정과 다를 수 있다. 앱이 일정을 지정하면 출발 안내·대기 장소·경로 시작이 같은 일정을 본다.

## 결과

- 앱 요청 호환이 깨진다. 출발 안내·대기 장소는 `scheduleSeq`·`dayOfWeek`가 필수가 되고 `driveMin`은 받지 않으며, 경로 시작은 `scheduleSeq`가 필수가 된다. 응답은 `driveMin`·`driveSource`가 없어지고 `driveRoute`·`pickupArrivalDt`·`homeArrivalDt`·`waitingPlace`가 생긴다.
- 출발 안내·대기 장소 요청마다 카카오를 호출한다. 호출 비용과 지연이 생기고, 실패해도 직선 추정으로 응답한다.
- 출발 안내·대기 장소에는 시간 창이 없고 경로 시작에는 있어서, 하원 + 1시간이 지난 일정은 출발 안내가 200이어도 경로 시작이 101일 수 있다.
- P-01 명세(`docs/spec/`)의 출발 시각 식은 갱신되지 않았다. 명세 갱신은 PM 몫이다.
- 규칙은 `docs/api.md` "출발 안내 계산"·"오늘 픽업 계획"에 있다.
