# ADR-0024 — 실시간 통로는 SSE와 서버 메모리 허브, 차 위치는 메모리에만

- 상태: **채택** (2026-11-12)
- 사용자가 2026-11-12에 고른 결정이다(T44 설계, T51).

## 결정

- 아이 휴대폰 웹(픽업 안내)은 서버와 SSE(`text/event-stream`)로 연결한다(`GET /api/v1/Pickup/W/DetailChildPickupStream`). WebSocket을 쓰지 않는다.
  - 브라우저 `EventSource`는 요청 헤더를 붙일 수 없다. 링크 토큰은 `X-Pickup-Token` 헤더로만 받기 때문에(T40), 웹은 `fetch` 스트리밍으로 읽는다.
- 차량은 경로 시작부터 탑승 전까지 3초마다 위치와 내비 남은 시간을 보고한다(`PATCH /api/v1/Pickup/M/sign/UpdatePickupPlanPosition`). 서버는 그 값을 아이 화면에 바로 보낸다.
- 차 위치는 서버 메모리(`IPickupLiveHub`, 싱글턴)에 계획마다 마지막 하나만 둔다. DB·로그·`PICKUP_EVENT`에 남기지 않는다. 계획이 끝나면 지운다.
- 서비스는 계획 행이나 `PICKUP_EVENT`를 바꾸는 커밋 뒤에 허브에 "바뀜·끝남" 신호만 보낸다. 스트림 연결은 신호를 받으면 화면 데이터를 DB에서 다시 읽고, 직전과 다르면 보낸다. 이벤트 내용을 서비스마다 따로 만들지 않는다.
- 놓친 이벤트를 다시 보내지 않는다(`Last-Event-ID` 재생 없음). 다시 연결하면 화면 전체 스냅샷부터 받는다.
- 위치 기능은 `PickupLive:VehiclePositionEnabled`로 끌 수 있다. 기획의 위치정보 고지·동의 검토가 끝나기 전까지의 안전장치다.

## 근거

- 아이 화면은 서버에서 받기만 하면 된다(차 위치·상태 변화). 아이가 보내는 출발 알림은 요청 빈도가 낮아 기존 POST로 충분하다. 그래서 단방향인 SSE가 더 단순하다. .NET 10에 SSE 지원이 내장돼 있고 HTTP 그대로라 Tailscale Funnel·프록시를 지나기 쉽다.
- 차 위치는 부모의 이동 경로라 민감한 위치정보다. 화면에 필요한 것은 "지금 위치"뿐이라 이력을 남길 이유가 없다(사용자 결정: 마지막 위치만 메모리).
- 서버는 맥 한 대에서 컨테이너 하나로 돈다. 그래서 메모리 허브로 충분하다. 외부 메시지 브로커를 두면 운영할 것만 는다.
- 신호만 보내고 다시 읽으면, 화면 데이터를 만드는 곳이 조회 API와 한 곳으로 모인다. 서비스마다 이벤트 모양을 만들다 어긋날 일이 없다.

## 결과

- 서버를 여러 대로 늘리면 허브를 Redis pub/sub 같은 공유 통로로 바꿔야 한다. 그 전까지는 한 대 운영이 전제다.
- 서버가 재시작하면 차 위치가 비고 스트림이 끊긴다. 차량의 다음 보고(3초 안)에 위치가 다시 채워지고, 웹이 다시 연결하면 스냅샷부터 받는다.
- 커밋 뒤 신호를 빠뜨리면 그 변화는 다음 신호나 재연결 때까지 화면에 늦게 보인다. 그래서 계획을 바꾸는 새 경로를 만들 때는 신호를 붙인다(`docs/architecture/service.md`).
- Service는 `ResponseModel<T>`를 반환한다는 규칙(ADR-0004)에 스트림 읽기 메서드라는 예외가 하나 생긴다(`service.md`).
- 차량 SSE(`DetailPickupLinkStream`)도 같은 허브를 쓴다. 구독 상한은 아이·차량 대상별로 따로 센다(아이 화면 연결이 차량 연결을 밀어내지 않게). 기존 조회 API(`DetailPickupLinkStatus`)는 그대로 둔다.
- 규칙은 `docs/api.md` "아이 픽업 안내", `docs/security.md`, `docs/architecture/service.md`·`overview.md`에 있다.
