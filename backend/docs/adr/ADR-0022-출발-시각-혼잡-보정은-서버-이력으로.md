# ADR-0022 — 출발 시각 혼잡 보정은 서버 이력으로

- 상태: **채택** (2026-11-12)
- 설계: `personal_dev/wiki/projects/ride-mate/tasks/T18-files/설계-2026-11-12-congestion-design.md` (2026-11-12 승인). 구현은 T42.
- ADR-0018(도로 소통 수집은 n8n으로)에 TOPIS 월별 파일 1회 적재 예외 하나를 더한다.

## 결정

- 출발 안내(`DetailDepartureGuide`)의 "지금 출발" 차량 소요 시간은 앱이 보낸 `driveMin`을 쓴다. 앱은 Pleos NaviHelper `requestTrip`의 `eta`를 넣는다. (사용자 결정)
- "도착할 무렵 학원가 진입 구간이 지금보다 얼마나 더 막히는지"는 서버가 이력 집계표 `TRAFFIC_PROFILE`(학원가·요일·5분 칸별 대표 속도)로 보정한다. 보정분은 0~15분이고 출발을 늦추는 쪽으로는 보정하지 않는다. (사용자 결정: 이력 보정)
- TMAP 타임머신 길 안내와 카카오 미래 운행 정보는 쓰지 않는다. (사용자 결정)
- 집계표의 근거는 두 가지다. 우리 5분 수집 이력(`COLLECTED`, 같은 요일 3일 이상)을 먼저 쓰고, 없으면 TOPIS 도로별 일자별 통행속도 파일(`MONTHLY`, 대치동만)을 쓴다. 두 시각의 속도는 같은 출처끼리만 비교한다. (설계 판단)
- `COLLECTED`는 n8n 워크플로(`trafficProfile01`)가 매일 다시 만든다. `MONTHLY`는 n8n이 아니라 로컬 스크립트(`n8n/scripts/topis-monthly-load.py`)로 한 번 적재했다(2026-11-12, 2026-08~10월). 월 1회 자동 적재는 하지 않는다. (사용자 결정)

## 근거

- Pleos NaviHelper(v3.0.5)의 `requestTrip`은 출발 시각을 받지 않는다. 미래 출발 소요 시간을 차량 SDK로는 얻을 수 없다(2026-11-12 API 레퍼런스 확인).
- 카카오는 담당자 답변상 상업 이용이면 무료 한도 안이라도 제휴가 필요하고, 결과를 캐시·저장할 수 없다. TMAP은 무료가 하루 1,000건이고 상업 이용·저장 조건을 확인하지 못했다.
- 대치동은 TOPIS 월별 파일의 링크 ID가 우리 수집 링크와 같은 체계라(114개 중 112개 일치) 수집 이력이 쌓이기 전부터 보정할 수 있다.
- 월별 파일은 35MB XLSX라 n8n으로 읽으면 한 달 치만으로도 Docker 메모리 부족으로 종료됐다(exit 137, OOMKilled). 우리 수집 이력이 약 3주 쌓이면 하원 시간대(14~24시)는 `COLLECTED`가 덮으므로, 월별 파일은 임시 근거로 한 번 적재하는 것으로 충분하다.

## 결과

- 서버는 요청 중에 외부 교통 API를 부르지 않고 `TRAFFIC_PROFILE`만 읽는다.
- 응답 필드는 바뀌지 않는다. 보정분은 `departureDt`·`slackMin`에 들어가고, 보정했으면 `reasons`에 `ROAD_CONGESTION`(`congestionMin`, `areaCode`)이 붙는다. 대기 장소 추천에는 보정을 넣지 않는다.
- 평촌은 공개 과거 이력을 찾지 못해 우리 GITS 수집이 같은 요일 3일 이상 쌓일 때까지 보정하지 않는다.
- `MONTHLY` 값은 2026-08~10월로 고정된다. 다시 넣으려면 `n8n/README.md` "TOPIS 월별 통행속도 1회 적재" 절차를 따른다.
- 진입 구간 길이(1.5km)와 상한(15분)은 가정값이다. 실제 픽업 기록이 쌓이면 다시 맞춘다.
